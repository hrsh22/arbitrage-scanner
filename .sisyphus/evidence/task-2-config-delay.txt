Task 2: Config Delay Evidence
==============================

Summary:
Implemented config delay mechanism (anti-gaming) in EpochMath library with 2-epoch default
delay to prevent same-epoch parameter gaming.

Implementation:
---------------

1. EpochMath.getConfigActivationTime()
   - Calculates (effectiveEpoch, effectiveTimestamp) for config changes
   - Formula: currentEpoch + 1 + activationDelayEpochs
   - Default delay: 2 epochs

2. EpochMath.shouldUseOriginalConfig()
   - Determines if queued request uses original or new config
   - Returns true if requestQueueEpoch < configEffectiveEpoch
   - Prevents gaming by queuing right before config change

3. WeeklyEpochVault Integration:
   - Added DEFAULT_CONFIG_DELAY_EPOCHS constant (value: 2)
   - Added PendingConfigChange struct to track scheduled changes
   - Added scheduleConfigChange() function (admin only)
   - Added canApplyConfigChange() view function
   - Added cancelConfigChange() function (admin only)
   - Added getPendingConfigChange() view function
   - Added onlyWhenConfigEffective modifier

Anti-Gaming Rules:
------------------
1. Config changes NEVER affect the current epoch
2. Config changes take effect after: next epoch + delay epochs
3. Requests queued before config effective epoch use ORIGINAL config
4. Requests queued at or after config effective epoch use NEW config
5. Delay is deterministic and publicly verifiable

Test Results:
-------------
All config delay tests pass:
- test_ConfigActivationTime_DefaultDelay: effective epoch = current + 1 + 2
- test_ConfigActivationTime_ZeroDelay: effective epoch = current + 1
- test_ShouldUseOriginalConfig_True: request epoch < config effective epoch
- test_ShouldUseOriginalConfig_False: request epoch >= config effective epoch
- test_ShouldUseOriginalConfig_SameEpoch: boundary case
- test_ConfigActivation_DeterministicAcrossEpochs: 5 epochs tested
- test_AntiGaming_SameEpochRequests: proves same-epoch protection
- test_AntiGaming_DeterministicBoundaries: fuzz-like boundary testing

Boundary Edge Cases Tested:
---------------------------
1. Config proposed at last second of epoch N
   - Effective epoch = N + 3 (not N+1 or N+2)
   - Request in epoch N uses ORIGINAL config

2. Config proposed at first second of epoch N
   - Effective epoch = N + 3 (same formula)
   - Request in epoch N uses ORIGINAL config

3. Zero delay (activationDelayEpochs = 0)
   - Effective epoch = current + 1 (next epoch)
   - Still provides minimum 1-epoch protection

Maple Pattern Reference:
------------------------
Following Maple's cyclical withdrawal pattern:
- Config changes proposed in cycle N
- Effective after cycle N + 1 + delay
- Prevents last-minute gaming attacks
- All participants have visibility into pending changes

Events Emitted:
---------------
- ConfigChangeScheduled(parameterHash, effectiveEpoch, proposedAt)
- ConfigChangeActivated(parameterHash, effectiveEpoch)
- ConfigChangeCancelled(parameterHash)

Errors Defined:
---------------
- ConfigChangeAlreadyPending(parameterHash)
- ConfigChangeNotYetEffective(parameterHash, currentEpoch, effectiveEpoch)
- NoPendingConfigChange(parameterHash)
