================================================================================
1. IMPLEMENTATION SUMMARY
================================================================================

Modified freezeEpoch() to transition requests to Frozen status:
  - Iterates through all pending redemption requests in current epoch
  - Transitions each Pending request to Frozen status
  - This is the explicit boundary between mutable and immutable cohorts

Modified cancelRedeemRequest() to block frozen requests:
  - Explicit check: if (request.status == RequestStatus.Frozen) revert
  - New error: CannotCancelFrozenRequest(uint256 requestId)
  - Secondary check: epoch.status must still be Active

Added new error type:
  error CannotCancelFrozenRequest(uint256 requestId);

2. CODE LOCATIONS
================================================================================

Contract: contracts/src/EpochTrancheVault.sol

freezeEpoch() - Request status transition (lines 318-324):
  // Transition all pending redemption requests to Frozen status
  uint256[] storage requests = epochRedemptionRequests[currentEpochId];
  for (uint256 i = 0; i < requests.length; i++) {
      RedemptionRequest storage request = redemptionRequests[requests[i]];
      if (request.exists && request.status == RequestStatus.Pending) {
          request.status = RequestStatus.Frozen;
      }
  }

  // Explicit guard: Frozen requests cannot be cancelled
  if (request.status == RequestStatus.Frozen) {

================================================================================
3. STATE TRANSITION DIAGRAM
================================================================================

Redemption Request Lifecycle:

  Pending ──freezeEpoch()──> Frozen ──settleEpoch()──> Claimable ──redeem()──> Claimed
      │                         │
      │ cancelRedeemRequest()   │ (blocked)
      ▼                         │
  Cancelled ◄───────────────────┘

Transition Rules:
  1. Pending -> Frozen: Automatic at epoch freeze (by freezeEpoch)
  2. Pending -> Cancelled: Only if epoch still Active (before freeze)
  3. Frozen -> Cancelled: BLOCKED (CannotCancelFrozenRequest error)
  4. Frozen -> Claimable: Automatic at settlement (by settleEpoch)
  5. Claimable -> Claimed: Via redeem() or withdraw()

5. ANTI-GAMING PROPERTIES
================================================================================

G1: No Front-Running
    Once freeze occurs, users cannot cancel to avoid unfavorable settlement terms.
    The cohort is locked and all participants share the same outcome.

G2: No Selective Exit
    Users cannot cherry-pick out of the redemption cohort after freeze.
    This ensures pro-rata distribution fairness.

G3: Clear Boundary
    The explicit transition to Frozen status provides an on-chain audit trail
    of exactly which requests were included in each settlement cohort.
