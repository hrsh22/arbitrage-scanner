SECTION 6: FULL LIFECYCLE WALKTHROUGH
================================================================================

SCENARIO: User deposits, redeems, and claims through full epoch cycle

6.1 PHASE 1: DEPOSIT
--------------------
1. User calls queueDeposit(1000 USDC)
   - Contract: EpochTrancheVault.queueDeposit()
   - Event: DepositQueued(requestId=1, depositor=user, assets=1000 USDC, targetEpoch=1)
   - State: DepositRequest created with targetEpoch=1

2. Admin calls processDepositQueue(epochId=1, 0, 100)
   - Contract: EpochTrancheVault.processDepositQueue()
   - Calculation: shares = (1000e6 * 1e18) / currentNAV
   - Event: DepositProcessed(requestId=1, sharesMinted, epochId=1)
   - State: Shares minted to user, DepositRequest marked processed

6.2 PHASE 2: REDEMPTION REQUEST
-------------------------------
1. User calls requestRedeem(500 shares, user, user)
   - Contract: EpochTrancheVault.requestRedeem()
   - Validation: Epoch 1 is Active, NAV is fresh
   - Event: RedeemRequest(controller=user, owner=user, requestId=101, shares=500)
   - State: RedemptionRequest created with status=Pending, epochId=1

2. User monitors via GET /api/vaults/1/redemptions
   - Returns: pendingRequests with lifecycle fields
   - queued: 0 (not in deposit queue)
   - frozen: 0 (not yet claimable)
   - accrued: 0 (not settled)

6.3 PHASE 3: EPOCH FREEZE
-------------------------
1. Admin calls freezeEpoch(snapshotHash)
   - Contract: EpochTrancheVault.freezeEpoch()
   - Validation: Epoch 1 is Active, NAV is fresh
   - State: Epoch 1 status=Frozen, snapshotNAV recorded
   - State: Epoch 2 created with status=Active
   - Event: EpochFrozen(epochId=1, snapshotHash, nav, timestamp)

2. RedemptionRequest status automatically becomes Frozen
   - Backend maps contract status 1 to "frozen"

6.4 PHASE 4: EPOCH SETTLEMENT
-----------------------------
1. After epoch end time, admin calls settleEpoch(1, availableAssets, carryAmount)
   - Contract: EpochTrancheVault.settleEpoch()
   - Validation: Epoch 1 is Frozen, block.timestamp >= endTime
   - Calculation: pro-rata ratio if needed
   - State: Epoch 1 status=Settled, totalAssetsAvailable set, carryAccrued set
   - State: RedemptionRequest status=Claimable, assetsClaimable calculated
   - Event: EpochSettled(epochId=1, totalShares, totalAssets, carryAmount, proRataRatio)

2. User checks GET /api/vaults/1/carry-eligibility
   - Returns: accrued (from entitlement), claimed, claimableNow
   - meetsThreshold: true if claimableNow >= 100 USDC

6.5 PHASE 5: CLAIM
------------------
1. User calls redeem(requestId=101, shares=500, receiver=user)
   - Contract: EpochTrancheVault.redeem()
   - Validation: Request is Claimable, shares <= request.shares
   - Calculation: grossAssets = (500 * totalAssetsAvailable) / totalSharesPending
   - Calculation: carry = (grossAssets * carryAccrued) / 1e18
   - Calculation: netAssets = grossAssets - carry
   - Validation: netAssets >= MIN_CLAIM_THRESHOLD (100 USDC)
   - State: request.shares -= 500, request.carryDeducted += carry
   - State: If request.shares == 0, status=Claimed
   - Transfer: netAssets USDC to receiver
   - Event: Withdraw(sender, receiver, controller, netAssets, 500)

2. Backend records claim in entitlement ledger
   - entitlementRepository.incrementClaimed(entitlementId, netAssets)

6.6 PHASE 6: FINAL DUST CLAIM (if any remaining)
------------------------------------------------
1. User has small remaining claim < 100 USDC threshold
   - Cannot claim individually due to BelowClaimThreshold error

2. User waits and accumulates more claims across epochs
   - Multiple epochs contribute to same entitlement
   - claimableNow aggregates across all epochs

3. Once claimableNow >= 100 USDC, user claims again
   - Same process as Phase 5

6.7 PHASE 7: EPOCH FINALIZATION
-------------------------------
1. Admin calls finalizeEpoch(1)
   - Contract: EpochTrancheVault.finalizeEpoch()
   - Validation: Epoch 1 is Settled
   - State: Epoch 1 status=Finalized
   - Event: EpochFinalized(epochId=1)

SECTION 7: STATE MACHINE VALIDATION
================================================================================

7.1 REDEMPTION REQUEST STATE MACHINE
------------------------------------
Contract states (uint8):
  0: Pending  -> Can cancel, can view
  1: Frozen   -> Cannot cancel, awaiting settlement
  2: Claimable -> Can claim, can view
  3: Claimed  -> Terminal state
  4: Cancelled -> Terminal state

Valid transitions:
  Pending -> Frozen (on epoch freeze)
  Pending -> Cancelled (on cancelRedeemRequest)
  Frozen -> Claimable (on epoch settlement)
  Claimable -> Claimed (on redeem/withdraw)

7.2 EPOCH STATE MACHINE
-----------------------
Contract states (uint8):
  0: Active   -> Accepting deposits and requests
  1: Frozen   -> Snapshot taken, no new requests
  2: Settling -> Settlement in progress (optional)
  3: Settled  -> Claims available
  4: Finalized -> Terminal state

Valid transitions:
  Active -> Frozen (on freezeEpoch)
  Frozen -> Settled (on settleEpoch)
  Settled -> Finalized (on finalizeEpoch)

7.3 CLAIM STATE MACHINE (Backend)
---------------------------------
Backend states (from claimStateMachine.ts):
  OPEN -> PENDING_CLAIM (claim initiated)
  PENDING_CLAIM -> CLOSED (claim confirmed)
  OPEN -> CANCELLED (request cancelled)

Guard conditions:
  - Only owner/controller/operator can claim
  - Must be in Claimable contract status
  - Must meet minimum threshold
