# Task 4: Early Mint Guard Evidence

## Summary
Implemented guard to prevent minting before target epoch opens in EpochTrancheVault.sol.

## Guard Implementation

### Location: processDepositQueue function (Lines 333-334)
```solidity
// Guard: epoch must have opened (epochOpenNAV set) to process mints
if (epoch.epochOpenNAV == 0) revert EpochNotActive(epochId);
```

## How the Guard Works

### 1. Epoch Creation Sets epochOpenNAV
When `freezeEpoch` is called and creates the next epoch:
```solidity
uint256 nextEpochId = currentEpochId + 1;
epochs[nextEpochId] = Epoch({
    // ...
    epochOpenNAV: currentNAV,    // Snapshot NAV at epoch open for mint pricing
    // ...
});
```

### 2. Epoch 0 Initialization
Epoch 0 (deployment) is initialized with:
```solidity
epochs[0] = Epoch({
    // ...
    epochOpenNAV: 1e18,          // Initial NAV for first epoch minting
    // ...
});
```

### 3. Guard Check
Before processing any deposit queue, the guard verifies:
- `epoch.epochOpenNAV != 0` - ensures the epoch has been opened
- If epochOpenNAV is 0, it means the epoch hasn't been created yet (freezeEpoch not called)

## Security Properties

### Property 1: No Minting Before Epoch Exists
- Deposits are queued for `targetEpoch = currentEpochId + 1`
- But minting is blocked until `freezeEpoch` creates that epoch with `epochOpenNAV`
- This ensures deposits are only minted when the target epoch is officially open

### Property 2: Single Mint Per Request
- Each `DepositRequest` has a `processed` boolean flag
- Once processed, subsequent calls to `processDepositQueue` skip already processed requests
- This ensures requests are minted exactly once

### Property 3: Consistent Pricing Within Epoch
- All deposits for a given epoch use the same `epochOpenNAV` value
- This prevents gaming the system by timing deposits based on NAV fluctuations

## Test Scenario

### Before Fix (Vulnerable)
1. Epoch 0 is active
2. User queues deposit for epoch 1
3. Attacker calls `processDepositQueue(1, ...)` before epoch 1 opens
4. Minting happens with current NAV (potentially different from epoch-open NAV)

### After Fix (Protected)
1. Epoch 0 is active
2. User queues deposit for epoch 1
3. Attacker calls `processDepositQueue(1, ...)` before epoch 1 opens
4. Transaction reverts with `EpochNotActive` because `epochOpenNAV == 0`
5. Only after `freezeEpoch` is called (setting `epochOpenNAV`) can deposits be minted

## Verification
- Guard is checked before any minting operations
- Guard uses the same `EpochNotActive` error for consistency
- Contract compiles and guard logic is sound
